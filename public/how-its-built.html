How it's built.

Trail.AI is a personal training dashboard that turns Strava data into endurance metrics, then lets an AI coach reason over those numbers. This page walks through the engineering: the metrics engine, the agent design, the security model, and how it's tested. Full source on GitHub.

The stack

BrowserStatic HTML, vanilla JS and Chart.js. No framework, no build step, no secrets.
Vercel serverless functions (Node)Strava OAuth, encrypted session, metrics engine, prompt builder, agent loop, rate limiting.
Strava APIActivities, laps and second-by-second streams (heart rate, pace, altitude).
Claude API (Anthropic)The coach. Sonnet for the signed-in athlete, Haiku for the public demo.

Metrics before words

The coach never sees raw GPS files or guesswork. Every session is first reduced to computed metrics by one module of pure functions, shared verbatim between the browser (for the charts) and the server (for the agent's tools), so the number on a chart and the number in a coaching answer can never diverge. Both speak the same five plain questions:

  • Load vs usual - heart-rate load of the last 7 days against the average week of the 4 before. Big spikes are what get runners hurt.
  • Easy share - the share of running time in heart-rate zones 1-2. Around 80% keeps hard days hard.
  • Climbing speed - vertical metres per hour on sustained climbs (50 m or more at 3% grade or steeper), found from altitude streams.
  • Aerobic engine - pace at your easy heart rate, from flat easy runs only, so hills never inflate it.
  • Cardiac drift - heart-rate rise across a steady flat run, after warm-up. Under 5% means durable endurance.

Behind the plain names are standard sports-science tools: a Banister heart-rate load, acute-to-chronic load ratio and efficiency factor. They stay inside the engine; the interface and the coach never use the jargon.

Race readiness, scored by the weakest link

Two rules of thumb over the last 12 weeks against a target race: longest run (against two thirds of the race distance up to 60 km, and against about 5.5 hours of time on feet for ultras, where the distance rule stops scaling) and biggest climbing week against the race D+. There is no average, because an average hides the problem: the score is the weaker of the two and the card leads with the limiting factor. Climbing speed is shown for context only, since training speed on short fresh climbs is not comparable to race-average speed. The demo uses a fictional race; the owner's real race lives in a server-side setting, never in the browser, so the coach only ever sees server-side data.

The coach is an agent, not a completion

One model call decides for itself what it needs. There is no router and no forced tool use: the system prompt carries a cached summary of the athlete's current state (load vs usual, easy share, climbing speed, aerobic engine, last 15 sessions), which answers most questions on its own. For anything beyond that, the model has three tools:

list_activities

Sessions in any date window, filtered by sport. Covers history, specific months and period comparisons.

get_activity_details

Second-by-second analysis of one session: zones, kilometre splits, laps, cardiac drift.

compute_stats

Deterministic metrics - summary, climbing-speed trend, aerobic-engine trend, weekly volume, race readiness - computed by the same functions the dashboard uses.

The loop is capped at eight model calls per question, and the final call is always made without tools, so the model must end in a written answer. Live Strava calls are separately budgeted at six per question, which keeps latency and API usage predictable.

Honest progress, live text

The "Fetching activities…" lines in the chat are built only from the model's tool-call blocks - name and inputs - so the interface shows what the agent actually did, never what it claimed it would do. The answer itself is streamed token by token over server-sent events, on top of the agent's steps.

Grounded, not trusted

The browser sends only the conversation text. The server fetches the athlete's data itself, computes the metrics and builds the prompt. A user cannot inject fake training data into the coach's context, and the system prompt requires every recommendation to cite a number from it.

Security and privacy

  • Secrets never reach the browser. The OAuth exchange and token refresh run server-side. The session is a single AES-256-GCM encrypted cookie (httpOnly, Secure, SameSite=Lax) - stateless, so there is no database of tokens to leak.
  • Private context is owner-only. Injury history and goals live in an environment variable and enter the prompt only when the authenticated Strava athlete id matches the owner's. Never committed to the repo, never sent to the browser.
  • Defensive defaults. OAuth state check, strict validation of every chat message (roles, alternation, length), model output escaped before rendering, and a restrictive Content-Security-Policy with security headers on every response.
  • Cost and abuse controls. The demo runs on the smaller Haiku model with per-IP and global daily rate limits, and the system prompt is cached across turns (prompt caching) so repeated questions stay cheap.

One code path, two athletes

The demo is a fictional athlete: 16 weeks of synthetic but realistic training, generated by a seeded deterministic PRNG into Strava-shaped objects. Because demo and live data share the same shape, the same analytics, prompt builder, agent and UI run on both. The demo isn't a mock - it's the full product, and it doubles as a permanent integration test.

How it's tested

62 unit and integration tests (node:test, no framework) cover the metrics functions, race readiness, the session crypto, and the whole agent loop against a mock model - tool selection, visible-step labels, streaming, budgets and the forced final answer. On top of that, an 11-question evaluation harness (npm run eval) runs real questions through the real model against demo data, checking that the coach reaches for the right tool for each kind of question.

Every change ships the same way: a branch, tests green, the Vercel preview checked on desktop and mobile, and only then a merge - the live site is on my CV, so it doesn't break.
